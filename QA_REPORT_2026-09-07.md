## 2. Findings

### 🔴 F1 — Back press leaves the sidebar showing the previous section's actions

**Regression, introduced by this session's own commit `3dbcf7a`.**

On both tablet tiers, pressing Back returns to Flash but the sidebar keeps
whatever actions belonged to the section being left.

| From | After Back | Sidebar shows |
|------|-----------|---------------|
| Alerts | Flash | `Keyword alerts`, `Mark all as read` — stale |
| Bookmarks | Flash | *nothing* — Refresh, Search and Mark all as read are all gone |

Reproduced on the Large Tablet AVD at 1067 dp and again on the Medium tier.

**Cause.** Five paths change `_currentIndex`; only one tells the controller.
`_navigateTo` calls `SectionActionsController.instance.selectSection(index)`,
but the three back handlers and two jump-to-section helpers set the index
straight through `setState`:

| Location | Path | Affected |
|----------|------|----------|
| `lib/app.dart:846` | back press — three-column shell | ✅ yes |
| `lib/app.dart:986` | back press — rail shell | ✅ yes |
| `lib/app.dart:1006` | back press — phone shell | no sidebar, harmless |
| `lib/app.dart:691` | `_onAlertsRequested` (alert notification tap) | ✅ yes, all sidebar tiers |
| `lib/app.dart:715` | `_finishOnboarding` | ✅ yes, first run only |

The alert-notification path matters beyond Back: tapping an alert notification
jumps to Alerts carrying the previous section's actions.

**Recovers** when the user taps any rail destination, since that goes through
`_navigateTo`. **Scope:** Expanded and Medium tiers plus TV. Phones are
unaffected — they have no sidebar.

### 🟡 F2 — Adding a blocklist keyword does not refresh the article list

The keyword is stored and matching articles are marked blocked in the database
— the panel immediately reports the match count — but the article stays on
screen and the chip counts do not move. Switching sections does not clear it
either, because the four screens are kept alive in an `IndexedStack`. Only a
full app restart applies the block.

Reproduced twice via Filter → Keyword Blocklist → Add keyword:

| Keyword | Panel reports | List | Chip count |
|---------|---------------|------|------------|
| `Dolly` | 1 article | unchanged | All (35) → All (35) |
| `Bentley` | 1 article | unchanged | All (36) → All (36) |

After force-stop and relaunch, both articles were gone.

**Not a matcher bug.** `ArticleRepository.retroactivelyBlock`
(`lib/repositories/article_repository.dart:484`) runs and sets
`is_blocked = 1`; every list query already filters on it. The gap is purely
the UI not reloading.

Worth contrasting with keyword **alerts**, which do update live — adding
`iphone` and `openai` moved the Alerts badge from 4 to 10 immediately. The
alerts path has a notifier the blocklist path is missing.

### 🟡 F3 — BBC's consent dialog is not caught by the banner suppression

`_kHideConsentBannersCss` (`lib/widgets/article_detail_pane.dart:45`) covers
OneTrust, Cookiebot, Quantcast, TrustArc and Didomi, plus generic
`cookie-consent` / `cookie-banner` class and id fallbacks. BBC News uses none
of those, so its full-page "Let us know you agree to advertising cookies"
modal (54 partners) sits over the article in the built-in viewer, with a
second banner along the bottom. BBC News is one of the feeds in the test set.

**The mechanism works** — TechRadar's CMP is suppressed cleanly, proven by
loading the same URL in Chrome side by side, where the "We value your privacy"
modal appears and in Flash it does not. This is a selector-coverage gap, not a
broken feature.

### ℹ️ F4 — The Alerts badge counts every entry, not unread ones — *by design*

Marking all alerts read dims every card but leaves the badge at 10. This is
deliberate and documented at `lib/app.dart:695`:

> `totalEntryCount()` — every entry, read and unread alike — because that is
> exactly what the Alerts pill showed before it became a destination.

Raised only because a red badge that never clears is an unusual convention.
**Not a defect, and it should not be "fixed" without a product decision.**

---

### ℹ️ F5 — A raw error code is shown to users when Nano is unavailable

The explanation above it is good — "On-device AI is not available on this
device. Gemini Nano requires a Pixel 8 or newer running Android 14+."
Directly beneath, in red, sits `NANO_UNAVAILABLE: Feature status: 0`. Seen on
both the Samsung and the Lenovo. Useful for support, developer-facing for
everyone else.

---

### ℹ️ F6 — Search and Settings cover the rail on tablets

Both push full-screen routes, so on a 1707 dp display the sidebar and reading
pane vanish for a search box. Consistent with phone behaviour, but it drops
the tablet frame at exactly the width where there is room to keep it.

---

### ℹ️ F7 — Each article card exposes two identical "Summary" semantics nodes

Every card reports `Summary` twice at the same coordinates in the semantics
tree, on every screen and every device. A screen reader would announce it
twice per card.

---

### ℹ️ F8 — A category chip disappears at zero unread

After marking a chip-filtered view read, that category's chip is removed from
the row unless it is the selected one — so those articles are no longer
reachable through the chips. Consistent with chips being unread counters, but
it means "Gaming" can vanish from the filter row entirely.

TechRadar's consent modal suppressed, verified against Chrome loading the same
