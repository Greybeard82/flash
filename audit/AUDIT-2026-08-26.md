# Flash — Master Audit

**Commit:** `87f50c3` (tree matched; only untracked file was `REMOVE_REDUNDANT_SETTINGS_PROMPT.md`)
**Date:** 26 August 2026
**Scope:** whole codebase — 79 files / 15,873 lines under `lib/`, 41 files / 7,421 lines under `test/`, Android host, docs.

---

## 1. Executive summary

The codebase is in good health. It analyses clean, 492 tests pass in 16 s and survive
randomised ordering, and six of seven hand-mutations of critical logic were caught by the
suite. The recent UX passes left the feed screen coherent. Most of what follows is at the
edges: the Android host, the destructive paths, and claims in the docs that the code no
longer supports.

Three things need attention before anything else:

1. **The release APK is signed with the universal Android debug key.** Every APK you have
   sideloaded to yourself and to friends is signed with a key that is on every developer
   machine on earth. You cannot ever replace it with a properly-signed build without an
   uninstall, which wipes the database. This gets worse every time you share a build.
2. **Android Auto Backup silently uploads `flash.db` to the user's Google account** — every
   feed, every article, every read timestamp, the entire blocklist — with no opt-in and no
   mention in the UI. The PRD's opening line is "All data lives on-device."
3. **Backup restore wipes the library before it has meaningfully validated the file**, in no
   transaction. A shape-valid but type-invalid JSON destroys everything and restores nothing.
   Mutation testing proves the guard is untested: deleting the `validate()` call breaks zero tests.

Nothing here is a crash, and nothing is losing data today.

## 2. Findings

### [SEV-1] Release builds are signed with the Android debug key

**Where:** `android/app/build.gradle.kts:36–41`
**What:** The `release` build type sets `signingConfig = signingConfigs.getByName("debug")`.
Confirmed on the built artefact: `apksigner verify --print-certs` reports
`Signer #1 certificate DN: C=US, O=Android, CN=Android Debug`.
**Why it matters:** Two consequences, both irreversible.
(a) Android identifies an app by package name + signing certificate. Any future build signed
with a real key is a *different app* to the OS: `adb install -r` fails with
`INSTALL_FAILED_UPDATE_INCOMPATIBLE`, and the only path forward is uninstall — which deletes
`flash.db` and every article, bookmark and read timestamp in it. Every device you have
installed on today is on that path.
(b) The debug keystore is not a secret; it ships with every Android SDK. Anyone can build an
APK that the OS will accept as an in-place update to Flash on your phone or your friends'.
**Confidence:** certain
**Fix shape:** Generate a real keystore, keep it and its passwords somewhere you will still
have them in five years, and wire it via `key.properties` (gitignored). Do it before sharing
another build. Accept that already-installed copies will need one uninstall-and-reinstall,
and consider shipping an OPML export reminder alongside that.

### [SEV-1] The whole database is uploaded to Google Auto Backup, contradicting the PRD

**Where:** `android/app/src/main/AndroidManifest.xml:21` (`android:allowBackup="true"`),
`android/app/src/main/res/xml/backup_rules.xml:7–9`,
`android/app/src/main/res/xml/data_extraction_rules.xml:7–15`
**What:** Both rule files explicitly `<include domain="database" path="flash.db"/>` — for
cloud backup *and* device transfer. `backup_rules.xml`'s own comment says "Restored
automatically on reinstall — no user action required."
**Why it matters:** Android Auto Backup is on by default and needs no consent beyond the
device-level Google Backup setting. So a user's complete reading history, subscription list
and keyword blocklist leave the device and sit in their Google account. That may well be what
you want — it is a nice reinstall story — but `PRD-Flash.md:15` says *"All data lives
on-device. Google Drive backup and local file backup are both available as **optional**,
non-destructive exports."* Both statements cannot be true. Nothing in the app tells the user
this is happening. For a product whose pitch is account-free and local-first, this is the
single most surprising thing in the repo.
**Confidence:** certain (configuration is unambiguous; whether it is *intended* is the open question)
**Fix shape:** Decide which claim is the real one. Either set `allowBackup="false"` and keep
the PRD's promise, or keep the backup and rewrite the PRD and onboarding to say plainly that
the database syncs to the user's Google account. Do not leave them contradicting each other.

### [SEV-1] Restore wipes the library before validating the file, with no transaction

**Where:** `lib/services/backup_serializer.dart:37–45` (`validate`), `49–65` (wipe), `66–104` (insert)
**What:** `restoreFromMap` calls `validate(data)` first — good — but `validate` only checks
`data['version'] == 1` and that `folders` and `feeds` are non-null. It does not check they are
`List`s, nor that entries carry the keys the loop then reads. The wipe runs next: every folder
is deleted, cascading to feeds and articles. Only *after* the library is gone does the code do
`(data['folders'] as List)` and `f['name'] as String`. There is **no transaction anywhere in
`lib/`** — `grep -rn "\.transaction(" lib/` returns nothing — so nothing rolls back.
**Why it matters:** A file like `{"version":1,"folders":{},"feeds":{}}` passes validation,
wipes everything, then throws a `TypeError` on the cast. The user is left with an empty app
and a backup file that will not restore. Same for any entry missing `name`, `title` or `url`.
This does not need malice — a truncated download or a hand-edited file does it.
Separately, restore destroys **every bookmark**, because the backup format carries only
folders, feeds and keywords (`backup_serializer.dart:9–35`) and bookmarks live in
`articles.is_saved`. The confirmation dialog warns that articles will be re-fetched
(`app_en.arb:101`); it does not warn about bookmarks.
**Confidence:** certain
**Fix shape:** Parse and fully type-check the whole payload into model objects *before* the
first delete, and wrap wipe-plus-insert in a single `db.transaction`. Add "your bookmarks
will be lost" to the confirmation string.

### [SEV-2] Mark-as-unread is unreachable from the UI

**Where:** `lib/widgets/article_card.dart:106` and `:115` (declared, never invoked);
`lib/screens/feed_screen.dart:1202` and `lib/screens/bookmarks_screen.dart:174` (handlers
passed in); `lib/widgets/radial_menu.dart:192,205,218,229` (menu is Bookmark / Share /
Summary / Close)
**What:** `ArticleCard.onMarkUnread` is accepted by the constructor and never called anywhere
in the file. The `Dismissible` calls `onMarkRead()` for **both** swipe directions
(`article_card.dart:262`). The radial menu has no unread action. The l10n key `markUnread`
exists in all five locales and is referenced by no widget.
**Why it matters:** Once an article is read, there is no way to mark it unread. Both screens
implement `_markUnread`, the repository implements `markAsUnread`, the string is translated —
the only missing piece is a button. `PRD-Flash.md` §4.3 documents this as a shipped feature
("**Mark as Unread — Swipe** — Long-press → radial menu, or dedicated swipe gesture"), and
`MANUAL_QA.md` §19 instructs the tester to "Swipe article 5 unread". Both describe something
that cannot be done. *That QA step is mine, written last pass from the PRD rather than from
the code — the exact mistake this audit is supposed to catch.*
**Confidence:** certain
**Fix shape:** Either add a fourth radial-menu action wired to the existing `onMarkUnread`, or
delete the parameter, the two handlers and the l10n key and correct both documents.

### [SEV-2] `minSdk` is 24, but ML Kit GenAI requires 26 and the PRD claims 26

**Where:** `android/app/build.gradle.kts:29` (`minSdk = flutter.minSdkVersion`),
`android/app/src/main/AndroidManifest.xml:17` (`tools:overrideLibrary`),
`PRD-Flash.md:31` and `:505`
**What:** `aapt2 dump badging` on the release APK reports `minSdkVersion:'24'`. The manifest
suppresses the resulting merge conflict with
`<uses-sdk tools:overrideLibrary="com.google.mlkit.genai.prompt,com.google.mlkit.genai.common"/>`,
whose comment says "ML Kit GenAI requires API 26+ but we handle unavailability gracefully at
runtime". The PRD states minimum SDK 26 in two places.
**Why it matters:** The app installs on Android 7.0 and 7.1 devices, where an ML Kit GenAI
class is present in the APK but built against APIs that do not exist. `overrideLibrary` silences
the build-time check; it does not make the library work. Whether the graceful runtime handling
actually holds depends on whether the failure surfaces as a catchable exception or as a
`NoClassDefFoundError` / verifier error at class-load — and `GeminiNanoPlugin.checkAvailability`
catches `Exception`, which does **not** catch `Error`. If it is the latter, opening the summary
sheet on an API 24–25 device crashes.
**Confidence:** likely (the version mismatch is certain; the crash-vs-graceful outcome is untested — see §5)
**Fix shape:** Pin `minSdk = 26` explicitly rather than inheriting Flutter's default. That
matches the PRD, removes the need for `overrideLibrary`, and costs a sliver of market share
that cannot run the headline feature anyway.

### [SEV-2] Cached thumbnails are decoded at full resolution into a 72×72 slot

**Where:** `lib/services/thumbnail_service.dart:45` (`await file.writeAsBytes(bytes)` — no
downscale), `lib/widgets/article_card.dart:343–346` (`Image.file(..., width: 72, height: 72)`
with no `cacheWidth`/`cacheHeight`)
**What:** The thumbnail service writes the downloaded bytes to disk verbatim. The card then
renders that file at 72×72 with no decode hint. Notably the *network* path right below it does
the right thing — `article_card.dart:357–358` sets `memCacheWidth: 144` and
`maxWidthDiskCache: 144` — so the care was taken once and missed on the path that is used
almost always, since the local file exists after the first fetch.
**Why it matters:** A 1920×1080 hero image decodes to roughly 8 MB of raster for a slot that
needs about 20 KB at 3× density. Flutter's default `ImageCache` is 100 MB, so about a dozen
such images fill it, and scrolling a long list thrashes decode continuously — on the app's
single hottest path, on the screen the whole product is built around. On a low-RAM device this
is an OOM candidate. There is also no cap on the thumbnail directory's size on disk.
**Confidence:** certain for the code path; the user-visible severity depends on real feed image
sizes and device RAM (see §5)
**Fix shape:** Downscale in `ThumbnailService` before writing, or pass
`cacheWidth: 144, cacheHeight: 144` to `Image.file` — ideally both, so old cached files
already on disk are also bounded.

### [SEV-2] A refresh where every feed fails reports success

**Where:** `lib/services/rss_service.dart:124–144` (per-feed `catch` absorbs everything),
`lib/services/refresh_service.dart:86–94` (`Future.wait` over calls that never throw),
`lib/screens/feed_screen.dart` `_reportRefreshFailure`
**What:** `fetchAndStore` catches every exception, records it on the feed row
(`consecutive_failures`, `last_fetch_error`, `is_dead`) and returns a normal record with
`newCount: 0`. So `Future.wait` never sees a rejection, `_doRefresh` returns normally, and
`refreshAll` never throws. The `try/catch` in `_fetchAndReload` / `_refreshCurrentTab` that
calls `_reportRefreshFailure()` is therefore unreachable for feed-level failures — which is
every realistic failure.
**Why it matters:** With no network, or on captive-portal wifi, the user pulls to refresh, the
spinner runs, the list resets to top, and nothing says anything went wrong. I saw exactly this
on-device during an earlier session: refreshing with aeroplane mode on reported "No new
articles. You're all caught up." The `refreshFailed` banner string exists and is translated
into five languages for a case that effectively cannot fire.
**Confidence:** certain (corroborated on device)
**Fix shape:** Have `_doRefresh` return a count of failed feeds alongside `totalNew`, and have
the screen show the banner when that count equals the number of feeds attempted (total failure)
or exceeds some threshold. The per-feed error recording is right and should stay.

### [SEV-2] Feed charset is assumed UTF-8

**Where:** `lib/services/rss_service.dart:86`
**What:** `utf8.decode(response.bodyBytes, allowMalformed: true)`. The HTTP `Content-Type`
charset parameter and the XML declaration's `encoding=` are both ignored, and
`allowMalformed: true` means invalid sequences become U+FFFD rather than raising.
**Why it matters:** A feed served as ISO-8859-1 or Windows-1252 — still common on older
European and regional sites, which is squarely this app's audience given it ships in five
European languages — renders every accented character as `�`. It fails silently and
permanently; there is no error and no retry that would fix it.
**Confidence:** certain for the mechanism; frequency depends on the user's feed list
**Fix shape:** Read the charset from the `Content-Type` header, fall back to sniffing the XML
declaration, fall back to UTF-8. Decode with the matching codec.

### [SEV-3] No `User-Agent`, no conditional requests

**Where:** `lib/services/rss_service.dart:79`, `:301`
**What:** `http.get(Uri.parse(feed.url))` with no headers at all. No `User-Agent`, no `ETag`
or `If-Modified-Since` handling, and no storage for either — `schema.md` shows no such columns
on `feeds`.
**Why it matters:** Two separate costs. Dart's default agent is `Dart/3.x (dart:io)`; a
non-trivial number of publishers and most Cloudflare-fronted sites block or challenge unknown
agents, so those feeds simply never work and land in the dead-feed counter with an opaque
error. And every refresh re-downloads every feed in full: 20 feeds at ~100 KB, every 30
minutes by default, is roughly 96 MB per day of entirely redundant transfer on a phone.
Conditional requests would make the common case a 304 with an empty body.
**Confidence:** certain
**Fix shape:** Set a descriptive `User-Agent` including a contact URL. Add `etag` and
`last_modified` columns to `feeds`, send them, and treat 304 as "no change".

### [SEV-3] Read-article secondary text fails WCAG contrast on the dark theme

**Where:** `lib/widgets/article_card.dart:155, 170, 189, 206`; palette at
`lib/theme/app_theme.dart:52` (`darkBg #0D1B2A`) and the dark `onSurface #E8E8E8`
**What:** Computed contrast ratios for read articles against the dark background:

| Element | alpha | ratio | verdict |
|---|---|---|---|
| Title (read) | 0.45 | **3.84** | fails AA (4.5) for 14 px body text |
| Source name (read) | 0.33 | **2.67** | fails |
| Timestamp (read) | 0.25 | **2.06** | fails |
| Reading time (read) | 0.20 | **1.75** | fails badly |
| Reading time (unread) | 0.38 | 3.12 | marginal |

Unread title (14.20) and unread source (5.82) are comfortably fine.
**Why it matters:** With Show read on — the default — read articles stay in the list for 48
hours, so this is not an edge case; it is a large fraction of what is on screen. At 1.75:1 the
reading-time text is essentially invisible to anyone with reduced contrast sensitivity, and
close to invisible in sunlight for everyone.
**Confidence:** certain (arithmetic on the actual constants)
**Fix shape:** Raise the read-state floors — roughly 0.6 for the title and 0.45 for secondary
text would clear AA — or drop the compounding second dim on already-muted `labelSmall` colours.

### [SEV-3] Migration steps 3 and 4 are not idempotent, and steps 2–7 are untested

**Where:** `lib/db/database.dart:94–100`; `lib/db/schema.dart:86, 89, 102`
**What:** The `oldVersion < 3` step runs `CREATE TABLE keyword_alerts` and the `oldVersion < 4`
step runs two `CREATE INDEX` statements, none of which use `IF NOT EXISTS` — unlike every
other DDL in the migration chain, which does (`database.dart:103, 161`). `migrateForTesting`
is only ever called with `fromVersion` 8, 10 and 11; nothing exercises 1 through 7.
**Why it matters:** sqflite wraps `onUpgrade` in a transaction, so an interrupted upgrade
should roll back and this is latent rather than live. But it is untestable by the existing
seam: calling `migrateForTesting(fromVersion: 2)` against a database `_onCreate` built at v12
throws, because `keyword_alerts` already exists. So the oldest upgrade paths — a v1 sideload
that has sat on a phone since the start, upgrading in one hop — are the ones with no coverage
at all, and cannot get any without changing the DDL.
**Confidence:** certain for the missing guards; "likely harmless in production" for the
transaction reasoning, which I could not verify directly
**Fix shape:** Add `IF NOT EXISTS` to those three statements. It costs nothing, matches the
rest of the chain, and immediately makes v1–v7 upgrades testable through the existing seam.

### [SEV-3] No global error handling

**Where:** nothing in `lib/` — `FlutterError.onError`, `PlatformDispatcher.instance.onError`
and `runZonedGuarded` are all absent
**What:** There is no top-level handler for uncaught framework or async errors.
**Why it matters:** In release, an uncaught widget exception paints a grey box where the
widget was and the app keeps running in a partly-broken state, with nothing recorded and no
way for the user to report it. An uncaught async error — for instance from one of the nine
`unawaited(...)` calls, several of which run DB writes — is swallowed entirely. You have no
crash reporting, so a defect that only manifests on someone else's phone is invisible to you.
**Confidence:** certain
**Fix shape:** Set `FlutterError.onError` and `PlatformDispatcher.instance.onError` in
`main()` to log, and decide whether to show a minimal in-app error surface. This does not
require a third-party crash service to be worth doing.

### [SEV-3] Nothing is transactional

**Where:** whole of `lib/` — `grep -rn "\.transaction(" lib/` returns nothing
**What:** No multi-write operation runs in a database transaction. This includes backup
restore (see SEV-1), OPML import, and `_markAllReadBody`, which does mark-all-read → cleanup →
network refresh → reload as four independent steps.
**Why it matters:** Any interruption leaves partial state. For mark-all-read the failure is
benign (articles marked read, cleanup skipped). For restore it is destructive. `insertArticles`
does use a batch (`article_repository.dart:18`), which is atomic-ish per commit, so the fetch
path is the one place this is handled.
**Confidence:** certain
**Fix shape:** Wrap restore and OPML import in `db.transaction`. Leave the refresh path alone —
a transaction spanning network I/O would hold a write lock for seconds.

### [SEV-4] Impeller is disabled with no recorded reason

**Where:** `android/app/src/main/AndroidManifest.xml:64–66`
**What:** `io.flutter.embedding.android.EnableImpeller` is set to `false`.
`git log -S "EnableImpeller"` attributes it to `3d5e449`, a large feature commit whose message
does not mention it. No comment, no issue reference.
**Why it matters:** Impeller is the default renderer on Android for a reason — it eliminates
shader-compilation jank, which shows up precisely on first scroll through a list. This app is
a scrolling list. The flag may have been added to work around a real bug (the dark-mode
thumbnail flicker fixed in `39bb6a6` is a plausible candidate, and that fix has since removed
the `BlendMode.saturation` that caused it). Nobody now knows, which means nobody will ever
dare re-enable it.
**Confidence:** suspected as to *why*; certain that the reason is unrecorded
**Fix shape:** Try a release build with the flag removed and scroll the feed hard on both
themes. If it is fine, delete the flag. If it is not, write down what breaks, right there in
the manifest.

- `flutter build apk --debug` and `--release` both succeed (200.2 MB / 58.3 MB).

- `SummaryCache` is **not** unbounded — `summary_cache.dart:26–28` does LRU eviction at `_maxEntries`.
- Network thumbnails are bounded (`memCacheWidth: 144`); it is only the local-file path that is not.
- `_setArticles` is genuinely the only writer of `_articles` — 12 call sites, `_syncCardKeys` has exactly one caller (inside the setter), no bare `_articles =` outside the declaration.
- HTTP has a 20 s timeout on both the feed and favicon paths; `package:http` follows a bounded 5 redirects and handles gzip transparently.
- `Feed.articleLimit` is now read (`rss_service.dart:67`) though still never written by any screen — the code comment at `:62` says so honestly.
- All fourteen `defaultSettings` keys other than `feedly_api_key` have live consumers.
- Cleartext HTTP is blocked by default (targetSdk 36, no `networkSecurityConfig`, no `usesCleartextTraffic`).
- `GeminiNanoPlugin`: `scope.cancel()` and `model?.close()` are both in `onDetachedFromEngine` (:34–35); `summarize` settles its `result` immediately (:150) and streams via `invokeMethod` with a `requestId` envelope, so double-`result` is structurally impossible on that path.

## 4. Could not check

- **WAL mode.** `onConfigure` sets only `foreign_keys`, so journal mode is the platform default. The release build is not debuggable so `run-as` cannot reach `flash.db`, and I cannot confirm whether a `-wal` file exists. This matters because both backup rule files exclude `-wal`/`-shm`: if WAL is on and a checkpoint has not run, the backed-up `flash.db` can be missing recently committed transactions. Needs either a debug build on a device or a `PRAGMA journal_mode` probe added temporarily.
- **`EXPLAIN QUERY PLAN` on the real queries.** Would have required creating a scratch database and harness; the brief permits creating only this report. Index coverage is therefore reasoned about, not measured — in particular whether `idx_articles_read_at` is actually chosen for the `is_read = 0 OR read_at >= ?` disjunction, which SQLite often cannot use an index for at all.
- **Whether ML Kit GenAI class-loading throws `Error` rather than `Exception` on API 24–25.** Determines whether SEV-2 (minSdk) is a crash or graceful. Needs an API 24 emulator.
- **Real cold-start time against the 1.5 s target**, and whether `runCleanup` on the cold path is a full scan.
- **TV behaviour** — no TV device or leanback emulator.
- **Google Drive backup**: scope requested, token storage, whether sign-out revokes. No Google account available.
- **Text scaling at 200%**, landscape, 360 dp, 800 dp, split-screen, foldables.
- **TalkBack semantics** on the article card and radial menu. Note the radial menu published *no* accessibility nodes at all when I dumped it on-device in an earlier session, which is suggestive but was not a TalkBack test.

Ordered by value. Each confirms or dismisses a finding above.

**1. Does the summary sheet crash on Android 7?** *(confirms/dismisses SEV-2 minSdk)*

**4. Memory under a long scroll.** *(quantifies SEV-2 thumbnails)*

## 6. Methodology

Static reading of all of `lib/`, `test/` and `android/`, plus:

- `flutter analyze` (bare), `flutter test`, `flutter test --test-randomize-ordering-seed random`, both APK builds.
- `aapt2 dump badging` and `apksigner verify --print-certs` against the built release APK, to get the *effective* `minSdk`, `targetSdk`, `versionCode` and signing identity rather than the declared ones.
- Seven hand-mutations of production logic, each reverted immediately; the working tree was verified clean after the sequence.
- Contrast ratios computed from the actual palette constants using the WCAG 2.x relative-luminance formula, alpha-composited against the real dark background.
- Dependency usage established by `grep -rl "package:<name>/" lib/` per package.

Two claims in the brief turned out to be wrong and are recorded in §3 rather than as findings:
`flutter_local_notifications` is genuinely used (keyword alerts fire), and `SummaryCache` is
bounded, not unbounded. `POST_NOTIFICATIONS` is requested at runtime. The
`LoadingController` English labels are never rendered.

No production file, test or document was modified. `git status` shows only this report.
